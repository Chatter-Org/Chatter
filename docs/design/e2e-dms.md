# End-to-end encrypted DMs

Identity keys, room keys and epochs, sealed messages, and what the server can and cannot see. Read before changing `routes/e2e.rs`, `packages/core/src/e2e/`, the message send/edit routes, or anything that reads a DM's message body.

## What is encrypted

- **Every DM and group DM created since this shipped, unless its maker turned encryption off** (`RoomRecord.e2e`, set in all three DM paths of `create_room` from the request's `e2e`, which defaults to `true`; the web client's New DM dialog has the switch). DMs from before stay plaintext: there is no migration.
- **A pair has at most two 1:1 DMs, one of each kind.** `dm_rooms` keeps the first under the bare pair and the other, once asked for, under `pair#e2e` or `pair#plain`. A request naming a kind reuses that kind's DM; one naming none (older apps, profile and friend buttons) reuses the first, whatever it is. Both share one streak (`DmRoomRecord::pair`). The DM list marks the encrypted one with a lock.
- **The text of messages, edits and thread replies, plus the quote of the message replied to.** Nothing else. The server still sees who is in a DM, who sent what and when, message sizes, reactions, pins, read markers, thread names, polls, and voice and video (the SFU terminates them).
- **Files are encrypted** (see Encrypted uploads below). The server sees that a file of some size was sent, not its name, type or contents. Voice messages recorded in the composer go the same way, but play as an ordinary audio file: the name that marks one is sealed, so there is no waveform player yet.

## Keys (`e2e/crypto.ts`)

- An **identity** is one random 32-byte seed. HKDF derives an X25519 key (to receive room keys) and an Ed25519 key (to sign) from it. The seed is the only secret, so it is all the backup carries.
- **Nobody chooses a passphrase.** The first time an account opens an encrypted DM with no identity (`status` `setup`), `E2eBanner` calls `autoSetUpE2e`: the client makes the seed and a **recovery key** (`newRecoveryKey`, 160 random bits as eight groups of four, no I/O/0/1) and seals the backup under that. `RecoveryKeyPrompt` (mounted in `App.tsx`) shows it once to copy, download or hand to the browser's password manager; it is kept on the device in `e2e-recovery:<user>` until the person says they kept it (so a reload cannot lose the only copy), and deleted on sign-out. A new device or a sign-out needs it typed or autofilled at the unlock dialog. `canonicalSecret` accepts it with any spacing, dashes or case; anything else is used as typed, so passphrases chosen before this still unlock. Resetting (`resetE2e`, Account settings → Encrypted Messages, or "Lost your recovery key?" while locked) makes new keys and a new recovery key the same way. The scrypt cost is kept for all backups; for a 160-bit secret it only costs time.
- The **backup** is the seed sealed with XChaCha20-Poly1305 under scrypt(secret), stored on the server (`e2e_identities`). Its AAD binds it to the account id. Whoever holds the database can guess at it offline, so new backups use `log_n` 17, `r` 8, `p` 1 (128 MiB a guess), and passphrases must pass `passphraseProblem` (12+ characters, not one repeated thing, not only digits). The parameters are stored with each backup — ones made at `log_n` 15 before this still open — and the server accepts `log_n` 14–20. The server never sees the passphrase: it is a separate secret from the login password, because the server sees the login password at every sign-in.
- **Replacing an identity takes a TOTP or recovery code; a first setup takes none** (`totp_code`, checked with `auth::verify_totp_or_recovery` only when `replace` is set). The first setup was relaxed so that turning encryption on needs nothing from the person. The cost: a stolen session token used *before* the real owner first opens an encrypted DM can make the keys and be handed those conversations. After that, only a reset can change them, and that needs the code. So an account with no 2FA can set up but cannot reset. Replacing is guarded because a session token alone used to be enough, and since members hand the current key to anyone with keys and no copy, a stolen token could replace an account's keys and be handed the conversation. A replacement also posts an `m.system` notice ("… reset their encryption keys") in each of the account's encrypted rooms.
- A **room key** is 32 random bytes per **epoch**. It is wrapped to each member with an ephemeral X25519 exchange and XChaCha20-Poly1305 (a sealed box), with room, epoch, recipient and maker in the AAD, and **signed by the member who made it**. The signature is what stops the server inventing a key: it can encrypt to anyone's public key, but it cannot sign as a member. Copies live in `e2e_room_keys`, one per (room, epoch, member).
- A **message** is `{body, reply_to_body?, mid, in_reply_to?, thread_id?, spoiler?}` as JSON, sealed under the epoch's key with room, epoch and sender in the AAD, and signed by the sender. `content.e2e = {v: 1, epoch, nonce, ct, sig}`. `mid` is a random id an edit keeps. Opening checks the sealed `in_reply_to` and `thread_id` against the event's, and that no other event carries the same `mid` (`bindingHolds`), so the server cannot replay a message, pass one message off as an edit of another, or move it to another reply or thread. The sealed `spoiler` replaces the event's. Messages sealed before `mid` existed carry none of this and are taken as they are.
- The server checks the byte lengths these produce (`is_key` in `routes/e2e.rs`). Change both sides together.

## Epochs

- A room starts at epoch `-1` and owes its first key. After that, **any membership change** (join, `add_to_dm`, leave, kick, ban, account deletion) sets `e2e_rotate` through `e2e::membership_changed` and broadcasts `m.e2e.rotate`. The next epoch keeps a removed member out of what follows and a new member out of what came before. New members get no history: that is by design.
- `POST /api/rooms/{id}/e2e/keys` either **starts** the next epoch or **hands out** the current one:
  - **Starting** requires that one is owed, `epoch` is current + 1, and there is a copy for exactly the members with keys (a missing or extra copy gets `M_E2E_MEMBERS`). It is a compare-and-set on the room, so when several online clients answer one broadcast, one wins and the rest get `M_E2E_EPOCH` and pick up the winner's key.
  - **Handing out** gives copies of the current epoch to members who have keys but no copy: someone who set up encryption after the epoch was made, or reset their keys. An existing copy is never overwritten.
- Starting an epoch is a compare-and-set on `e2e_epoch`, `e2e_rotate` **and `e2e_ver`**. `membership_changed` bumps `e2e_ver` on every change, and `encrypted_room_for_member` reads the room before the member list, so a key made from a list that has since changed is refused even when a rotation was already owed (otherwise a member kicked mid-rotation was handed the next key and `e2e_rotate` was cleared).
- **Replacing an identity also owes the room a new epoch** (`put_identity` calls `membership_changed`). Whoever holds the replaced seed holds the current key too; the next one is wrapped to the new keys only. The resetter's own client makes it; the others open it once they accept the change.
- A send, edit or thread reply into an encrypted room must be sealed under the current epoch, with no rotation owed. Otherwise the server answers 409 `M_E2E_EPOCH`. The client catches up (`recover` → `syncRoomKeys`) and reseals once (`sendMaybeSealed` in `api.ts`).
- **Plaintext into an encrypted room is refused** (`M_E2E_REQUIRED`), and a seal into a plaintext room is too. Older apps (Android until phase 4) therefore cannot send in new DMs, and they show the placeholder for what they receive. Silently storing their plaintext in a conversation everyone believes is private would be worse.

## Encrypted uploads (`e2e/files.ts`)

- The sender's client seals the file before it leaves (`apiUploadEncryptedFile`, chosen by `outgoingUploads` when the room is encrypted, and by `apiUploadFileForRoom` for anything posting a file outside that queue, such as the clip dialog; a new path that posts a file must use one of the two, because the server cannot see the link to check it): 1 MiB segments, XChaCha20-Poly1305 under a random per-file key, nonce = random prefix + segment number, last segment marked in the AAD (no reordering, dropping or truncating). It uploads the result as `<24 hex>.enc`, which the ordinary upload routes store untouched: no extension means no conversion, thumbnail, dimension probe or index. Every attempt uses a new key and name, so nothing resumes a half-sent earlier attempt, and a failed one's leftovers are discarded.
- The message body carries `<upload url>#k=<key>&t=<type>&s=<size>&n=<name>`. The fragment never goes to the server and the body is sealed, so the key, name and type are visible only to members, and the sender's signature vouches for them. The server cannot swap in another file: the key is in the signed message and every segment is authenticated. The text renderer already hides `/external/` links; `MediaPreview` draws them with `EncryptedAttachment`.
- **Only an upload on this server is an encrypted file** (`parseEncryptedFileLink`: the whole address must be `[origin]/external/<32 hex>/<name>.enc`, and `isServerUrl`). The file is fetched with the session, so a link to another site dressed as one used to hand the viewer's access token to whoever posted it, with no click, since pictures open on their own. Underneath that, `authenticatedFetch` refuses any URL that is not on this server, so nothing in core can send the token elsewhere.
- **The server enforces `.enc`.** `check_send` refuses (`M_E2E_PLAINTEXT_UPLOAD`) an attachment link not ending in `.enc` or carrying `#`/`?`, so a client that did not encrypt cannot put a plaintext file into the conversation. An edit may keep a plaintext file the message already carried (its folder is in the original body), so messages from before files were encrypted can still be edited.
- The client puts only `.enc` links in `attachments` (`uploadLinks`); a plaintext upload link someone pastes is just sealed text, and its file is not tracked as referenced by the message.
- Display: only `image/(png|jpeg|gif|webp|avif|bmp)`, `video/(mp4|webm|ogg|quicktime)` and common audio types are given to `<img>`/`<video>`/`<audio>`; anything else, **SVG included**, is a download. A blob URL of an SVG opened in its own tab would run as the app. Pictures up to 25 MB open on their own; video, audio and big pictures wait for a click; other files download on click. A file is fetched and opened whole in memory.
- Not hidden: the file's size and upload time, and that the server stores one. Forwarding a message to a plaintext room hands that room the key. The uploads list shows `.enc` names.

## What the server stores in place of the text

- `content.body` is `e2e::PLACEHOLDER_BODY`, followed by any upload links one per line. Everything that reads bodies — push, automod, link previews, message-link cards, the reply quote, upload referencing and purge — sees that and nothing else, so none of it needed a second code path. The links are what keep the uploads (`media::attachment_folders` reads bodies), and what an older app can still show.
- Push for an encrypted room says `e2e::PUSH_BODY` (Web Push payloads are not end-to-end encrypted to the member's keys).
- A user cannot send `m.system` or `m.watchparty` into an encrypted room (`check_msgtype`): sealed, they would draw as an unattributed notice ("X reset their encryption keys"). The client also shows every opened sealed message as `m.text`, since the type is not signed and a server could flip it. The server's own `m.system`, `m.watchparty`, `m.poll` and `m.poll_results` are left alone.
- Search for text and mentions skips sealed messages (`content.e2e` exists): their body is the placeholder, not their text. File and user search still work, and the client opens the results. Searching encrypted text would have to happen on the client, and is not built.
- Reports from an encrypted DM carry the placeholder. Moderators cannot read encrypted DMs, and message franking is not built.

## What the device does not take on the server's word (`session.ts`)

- **Contacts' keys are pinned** on the device the first time they are seen (`e2e-pins:<user>`). Keys that later differ go into `changedKeys` and the pinned ones stay in use: nothing is wrapped to the new keys, a new epoch is refused (`E2eKeysChangedError`) and none is handed out to them, and messages signed with them do not verify, until the person accepts the change (`acceptKeyChange`, the "Trust new keys" notice in `E2eBanner`). A real reset and a takeover look the same from here. Changes are noticed when keys are next fetched: on `m.e2e.identity`, or in a new session.
- **The device keeps its own list of who is in each encrypted room** (`checkRoster`, `e2e-rosters:<user>`), because keys go to members and membership is the server's word: a row written into the member list was handed the current key by every device on its next sync. The first time a device sees a room it takes the room as listed, which is what the person is shown. After that, someone the server adds is *new* until this device added them itself (`addToGroupDM` → `confirmMembers`) or the person confirms them ("They belong here" in `E2eBanner`). Until then this device hands them no copy, makes no epoch that includes them (`E2eNewMembersError`; the server takes an epoch only with a copy for every member with keys, so it waits), and does not send under a current key they made. Someone who leaves is dropped from the list, so coming back is new again. A member another member added is shown as new but is not blocked: the adder's device makes the next epoch with them in it, and the others send under it. The aim is to stop the *server* adding people, not to vet what members do.
- **The current epoch's key must come from a member whose keys have not changed** (`openCopies`), and who is on the roster. Older epochs, which are only read with, may come from someone who has since left, and may be signed by a key the maker has since reset away from and this device accepted (`pin.previous`). Without that, accepting a reset lost every epoch the person had made once the page reloaded, since room keys live in memory only. Anyone the server vouched for could otherwise hand this device a key and read what it sends.
- **Rooms once seen encrypted stay encrypted** (`e2e-rooms:<user>`): `noteRoomEncryption` only adds, and a sync that says otherwise throws rather than send in the clear.
- **A person's message without a seal in an encrypted room is `forged`** and its text is not shown, and a plaintext edit there is dropped (`m.e2e.ignored`). The server's own `m.system`, `m.poll` and `m.poll_results` are left alone. Webhooks are refused in encrypted rooms on the server (create and execute), since they post plaintext under any name.
- **A seed that no longer matches the server's keys is kept**, not deleted (`getKeysReplacedElsewhere`). The banner says the keys were changed from somewhere else. A server answer alone used to be able to wipe the device's keys.
- **Drafts never reach the server** for an encrypted room. The client keeps them in memory, and `set_draft` refuses them there whatever a client sends. `get_continuity` purges any saved before this.
- **No link previews** for encrypted messages: the server fetches previews, so it would learn the link.
- **Earlier keys still vouch for earlier messages.** Accepting a contact's new keys (or resetting your own) keeps the old signing key in the pin with `until` set to that moment. A message sent before then still verifies against it; one claiming to be sent after does not, since a key someone reset away from may be in other hands. `until` is compared with the server's `origin_server_ts`, so a server holding a stolen old key could backdate a forgery — the limit of what a device can check alone.

## The page around it

- A script running in the page can read the seed, so the client is served with a **Content-Security-Policy on scripts** (`content_security_policy` in `static_content.rs`): the bundle, the inline theme script by a hash computed from the file served, the Google Cast sender, wasm for the camera models, blob workers, and blob scripts (worklets fall under `script-src`, and the desktop app's screen-share audio worklet is a blob; only running script can make a blob URL). Nothing else, and no `unsafe-inline`. Images, media, connections and frames are deliberately left open — the client loads those from anywhere. Adding an inline script or a script host means changing the policy.
- The key routes are **rate limited** per account: setting up or replacing keys `E2E_IDENTITY` (5 an hour, which also bounds TOTP guessing there), querying and sharing keys `E2E_KEYS`.

## The client (`packages/core/src/e2e/session.ts`)

- Status: `setup` (never set up; set up automatically on opening an encrypted DM), `locked` (set up elsewhere, or signed out here), `ready` (this device holds the seed), `error`, or `off`. `startE2e` runs once per account on sign-in. A stored seed is used only if it still matches the server's public keys: a reset on another device makes it stale.
- The seed is kept through `host.secretGet/Set/Delete` (localStorage on the web and desktop, inert on mobile for now) and **deleted on sign-out**, so signing out and in on the same browser needs the recovery key again. Room keys are memory-only and fetched again each session.
- `api.ts` reaches the session through `e2e/hooks.ts`, because the session itself calls the API. Message loads (`apiGetMessages`, `apiGetMessagesAfter`, thread, pins, search) are opened there. Socket events are opened by `createE2eEventGate` in `wsHandler.ts` **before** anything reads them, so notifications, mentions and the timeline see the text. An event that needs a key fetched waits in line, and every event after it waits behind it, so a reaction or deletion never overtakes its message.
- An opened message has `content.e2e_state`: `ok`, `unverified` (it opens, but the signature does not match the sender's trusted keys — shown as "(unverified)"), `locked`, `missing` (no key for that epoch here, e.g. from before you joined), `broken`, or `forged` (see above). The last four replace the body with an `E2E_UNREADABLE` line.
- The reply quote is sealed inside the reply, taken from what the sender's client had opened. The server's `reply_to_body` is the parent's placeholder and is never shown.
- Socket events: `m.e2e.rotate` and `m.e2e.identity` (someone in the room can now be handed the key) make an online member's client sync the room after a random wait of up to 1.5 s, so they do not all race. `m.e2e.room_key` (a copy for you) syncs at once. Opening a DM and the first send also sync.

## Not built yet

- Phase 4: Android (keystore, `getRandomValues` polyfill, unlock UI). Until then Android shows encrypted DMs as locked and cannot send in them.
- Phase 5: fingerprint/safety-number verification. Keys are pinned on first sight, so a server that lies about someone's keys *from the start* (before this device ever saw them) is not caught. The recipient set of an epoch is not signed. The roster is per device and taken on first sight, so a member the server adds before a device first sees the room, a new device included, is taken as one; and a device cannot see whom another member's epoch was wrapped to. Signed membership changes would close both. Key history is per device: a device that never saw someone's old keys cannot vouch for their messages from before a reset.
- Encrypted files have no thumbnails, reserved layout space, streaming playback, waveform player or resumable upload; mobile cannot seal or open them.
- A member can hand another member who has no copy of the current epoch a key nobody else uses (first copy wins, and the server cannot tell). Group-DM denial of service, not a leak.
- No forward secrecy within an epoch, and no encrypted history for new members.
