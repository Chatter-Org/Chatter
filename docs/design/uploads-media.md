# Uploads and media processing

Upload lifecycle, conversion ladder (remux/re-encode), thumbnails, sizing, purge and sweep, resumable and concurrent uploads. Read before changing upload routes, media.rs/ffmpeg handling or the client upload queue.

Moved verbatim from the root AGENTS.md; keep it current when you change the behaviour it describes.

- `remux_with_subs` is a **ladder**, not one command: copy the video with every subtitle, then copy it with only the *text* subtitles (`probe_subtitles` returns those with their real subtitle-stream ordinal — using their position in the filtered list maps the wrong track), then re-encode with none. One command was all or nothing, so anything ffmpeg refused — a bitmap subtitle `mov_text` cannot take, a codec MP4 will not hold — failed the whole conversion and the upload kept the Matroska file. A browser handed one of those often renders the picture, finds an audio codec it cannot decode, and greys out the track selector: a video that plays silently
- The **picture** is checked the same way, against the same failure with the halves swapped. Copying a video stream only asks whether MP4 can *hold* the codec, and MP4 holds far more than a browser decodes — it has a tag for MPEG-4 Part 2, so an AVI carrying Xvid or DivX copies straight through, exits cleanly, keeps its audio, and plays as sound over a blank rectangle. `WEB_PLAYABLE_VIDEO_CODECS` is the allow-list a rung's output must land in or the ladder treats it as failed and re-encodes. It is an allow-list because the codecs that do not work are an open set. `hevc` is deliberately **off** it: it was kept to spare re-encoding iPhone videos, but outside Safari it draws only where the hardware decodes it, and on Linux (Chromium, Firefox, the Electron desktop app) almost nowhere — an HEVC MKV converted cleanly, kept its audio and thumbnail, and played as sound over a blank box
- A conversion that *failed* leaves no `.mp4`, and the serving path redoes it the next time anyone plays the file. One that succeeded **badly** leaves a file that looks finished, so it is recognised rather than merely missed: the same path re-converts an existing `.mp4` whose picture is undrawable, which is what repairs everything an older ladder let through. The answer is cached in a `.playable` marker beside it — that code runs on every range request and a scrubbed video makes dozens, so it is one probe per file rather than per request. The thumbnail is deliberately *not* regenerated: a re-encode keeps the picture and its shape, and touching it would drag in dropping the `.preview.webp` and re-recording dimensions for nothing
- Playable is a question about the **pixel format** as well as the codec: `picture_is_web_playable` holds `h264` to 8-bit 4:2:0, because High 10 and 4:2:2/4:4:4 H.264 are called `h264` and decode in no browser (anime rips, lossless screen recordings). MP4/MOV uploads go through the same check and are re-encoded when they fail it — they used to be faststarted and nothing else — and older ones are repaired in place the first time anyone plays them (`repair_unplayable_in_place`). The marker is `.browser-playable`, renamed whenever the check tightens so every file is asked again: `.playable` vouched for files under the codec-only check, `.web-playable` for HEVC, and both are ignored
- The serving path runs on every range request, so nothing it does may be repeated per request. A video with no captions gets an **empty** `@subs.json` (it used to get none, so every request re-ran an ffprobe), and a conversion or thumbnail that failed is remembered in `GAVE_UP` — in memory, so a restart, which is when a better ladder arrives, retries it. Before that, a file ffmpeg could not convert re-ran the whole ladder on every request, queued on the lock, and never started playing
- Audio is never what a rung gives up, and the result is **checked** rather than assumed — a conversion that exits cleanly having dropped the audio is treated as the failure it is, and the next rung runs. ffmpeg's stderr is kept on failure and logged; it used to go to `/dev/null`, so a conversion that failed left no trace anywhere
- A file whose conversion failed is still on disk as the original, and the serving path converts on demand when no `.mp4` is beside it — so a fixed ladder repairs what a broken one left, the next time anyone plays it
- Attachments are measured so a message can hold their space before they load, and the size is recorded at upload (`probe_image_dimensions`) plus a startup backfill for older ones. The sizing rule is `lib/mediaBox.ts`, not the markup: a `width`/`height` attribute is a *used* width, so a `max-height` clamp squashes the picture instead of shrinking it — the cap has to be restated as a bound on width, the axis that can give while keeping the shape. A **video** is measured through its `.thumb.jpg` rather than its own stream: the thumbnail is what the timeline lays out, ffmpeg has already baked rotation into it (a phone video reports itself landscape and displays portrait), and it is always 640 across. Same reason `thumbnailBox` takes no width bound from the record where `reservedBox` does
- `thumbnailBox` goes on the **container**, never on the picture, and the picture fills it (`w-full h-full object-contain`). A shrink-to-fit box with a dark background cannot be settled by sizing the thing inside it: a replaced element under a `max-height` contributes the width that cap implies *through its aspect ratio*, not the width it is drawn at, so a 16:9 thumbnail capped at 480 tall offered 853px to its parent while being drawn 640 — a black band down the right quarter of every landscape video in a column wider than 640px, with the play button centred on the box rather than the picture. Sizing the picture fixed a portrait one only by accident: its cap implies a *narrower* box than the picture, so the two happened to agree. One element holds the geometry and `object-contain` absorbs a thumbnail whose recorded shape has gone stale. Anything pinned to that container's edge (`CcControls`, the GIF favourite star) is measuring the same box, so it is right or wrong with it
- A thumbnail is not asked for through `toImagePreviewUrl`: it is already a 640px derivative, and it is generated **on demand from a request for the thumbnail itself**, so asking for `.thumb.jpg.preview.webp` both scales it back up and 404s for a video nobody has opened — a black box where the first frame goes. Regenerating a thumbnail (`fix_black_thumbnails`, and the on-demand path when `thumb_needs_update`) drops the `.preview.webp` beside it and calls `record_thumbnail_dimensions`: the new capture need not be the shape the old one was, and a record still describing the old one has every reader reserving a box the picture no longer fits
- Uploads are removed with what referred to them: redacting a message, deleting a room, and deleting an account (self or admin) all purge files through `media::purge_attachments` / `purge_user_uploads`. A message purge is doubly guarded — only files the sender uploaded, and only when no other unredacted message still references the file, because the same link can be pasted twice. `attachment_folders` matches conservatively: missing a file is survivable, deleting one still in use is not
- An upload is identified by the random **folder** it owns, not by its URL. One file has several names — the absolute URL it was handed back on, the same file through another hostname the instance answers to, a bare `/external/...` path — and a remux changes the filename, the disk path and the URL together. `attachment_folders` reads that folder out of a body and `purge_attachments` matches records on it. It matched the bare path only, while uploads have always been handed back absolute, so it found nothing in a real message and the purge behind it had never once run
- `remove_upload_record` deletes the upload's whole folder rather than naming sidecar suffixes. It is one file per random folder, so the folder *is* the upload; naming suffixes missed the `@N.vtt` subtitle tracks, and anything left behind then stopped the folder being removable at all
- `finalize_upload` is the shared tail of both upload paths, and it writes the `UploadRecord` **before** the conversions rather than after. A remux runs for minutes, and a restart during one used to leave a file on disk that no record named — invisible to the quota, the uploads list and every purge path, all of which work from records. The record carries `processing` until the work finishes and `folder` throughout, since that is the only field the conversions cannot move
- `complete` is idempotent. The staging dir outlives its chunks, holding a `done.json` with the resulting URL, so a client whose wait ran out during a remux asks again and gets the same URL — instead of uploading the file a second time and stranding the finished one. `upload_status` reports that dir as `status: "done"` with the URL, and the same sweeper collects it a day later
- `referenced_at` on an upload records that something keeps it — set by `send_message`, `edit_message`, `send_thread_message` and `set_profile`, and read by `sweep_unreferenced_uploads`. An upload that completes and is never posted is the one orphan nothing else can see, since it is indistinguishable from one still in use
- That sweep answers "is this definitely unused", never "did I fail to find a use". A candidate must have gone `UPLOAD_GRACE_SECS` unclaimed, and a pass that cannot read the references (`referenced_folders` answering `None`) deletes nothing at all. `collect_folders` walks whole documents rather than named fields, so the next field somebody adds does not quietly turn into a file deleted while in use
- It builds the reference set **once per pass**, not once per candidate: a regex over message bodies is a collection scan. In the steady state the claims mean there are no candidates and the scan never runs — it exists for the backlog from before claiming, worked through `UPLOAD_SWEEP_BATCH` at a time. On the default dry-run setting a pass finds the same files again, so it is throttled to daily rather than hourly
- `reclaim_unreferenced_uploads` (admin settings, default **off**) is what makes the sweep delete rather than report. A record it cannot judge — no folder, so nothing to look for — is marked referenced so the question is not re-asked every pass
- `reconcile_upload_folders` runs once at startup for the older shape: an `external/<folder>` with no record at all, which no purge path can see because they all work from records. Guarded by the 32-hex folder name and the same grace period, since this deletes directories
- An upload broken by a closed tab is offered back in the composer by `InterruptedUploads`, above the staged row — without it the chunks sit on the server for a day with nothing able to reach them. Resuming asks for the file again, because the bytes are not what the store keeps, and a file that is not the same one (`isSameFile`, the whole fingerprint) is refused rather than silently restarted: resuming onto the wrong bytes splices two files into one that assembles cleanly and will not open. `useInterruptedUploads` confirms each entry against the server, so a swept or finished upload is dropped rather than offered
- A row of files goes up `UPLOAD_CONCURRENCY` at a time through `runPool` (`lib/concurrency.ts`), used by both the outgoing queue and `useUploadQueue`. It ran one at a time on the reasoning that transfers would fight for one uplink — which missed that a file is not only sent: `complete` remuxes and probes it while the link sits idle, so a row spent most of its time sending nothing. Not all at once either: ten transfers sharing a link all finish about when the last would have anyway, each `complete` starts an uncapped ffmpeg pass, and every chunk in flight is a buffer held to be hashed
- `runPool` returns results in the order it was given them, never completion order — the urls are posted as the message, and the quickest file is not the one that should come first. It also never rejects: one file failing must not abandon the files beside it, so the caller models failure in the result type
- A send that carries files is handed to `lib/outgoingUploads.ts` and stops belonging to the composer that started it. The destination is read when Send is pressed and travels with the batch: the store's `sendMessage`/`sendThreadMessage` look up the *current* room as they post, so a large attachment used to arrive in whichever channel its author had wandered into while it uploaded. The batch lives in a module, so a room switch, a closed thread or an unmounted composer leaves it alone
- `OutgoingUploads` draws those batches above the composer in `ChatArea` and `ThreadPanel`, and one bound somewhere other than the view showing it says where — that label is what makes it safe to show every send from everywhere. A thread's batch is drawn by the thread panel while it is open and by the main composer when it is not, never both
- The staged row (`PendingAttachments`) is therefore only what has *not* been sent; `AttachmentTile` is the one piece of markup both rows draw, so the two cannot come to disagree about what a file looks like. `useUploadQueue` remains for the forum and showcase composers, which still upload in place
- Text with no attachment still sends synchronously, so a refusal — slow mode, a rate limit — puts what was written back in the composer. A batch that is refused keeps its text instead, on the batch, where a retry resends it
- Resuming stages the file on whichever composer the person is looking at rather than the one it started on — the record carries no room, and where it should land now is a better answer than where it was going an hour ago. It is the main `ChatArea` composer only; the thread, forum and showcase composers upload the same way but do not offer the list
- `check_storage_quota` counts staging bytes (`staging_bytes_for`) as well as records. Ten uploads started together each saw the same free space and all passed, because bytes in a staging dir are not a record yet
