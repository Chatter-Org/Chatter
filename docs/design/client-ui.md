# Client UI: themes, presence, sidebar, sounds, continuity

Theme and profile-theme rules, presence/idle, sidebar order and rail, channel column width, hover affordances, sounds, drafts/continuity and the composer. Read before changing those client areas or their server routes.

Moved verbatim from the root AGENTS.md; keep it current when you change the behaviour it describes.

- `can-hover` (`@custom-variant` in `index.css`, `(hover: hover) and (pointer: fine)`) means "reveal on hover where hovering exists, and stay visible where it does not" — a control with no other way of being reached must not hide behind a hover that never comes. The message action bubble is the **one** exception, because it does have another way: a "⋯" opening the same actions as a bottom sheet. So it renders only where hovering is possible and carries no touch fallback. Which surface a message shows is `touchActions = isMobile || !canHover`, and it has to be both — `useIsMobile` is a *viewport width* and this is a question about the *pointer*, so a tablet or a phone held sideways fell between them: wider than the breakpoint, so it got the bubble, and unable to hover, so the bubble never hid. Every message in the timeline carried a permanent row of buttons
- Cross-device continuity (`backend/routes/continuity.rs`): unsent drafts per `room|channel`, and video resume points. `GET /api/continuity` returns both in one call, fetched on mount and whenever the tab becomes visible. Drafts live in reducer state; resume points live in `resumePointsMap` (a module map beside `screenStreamsMap`) because a playing video reports its position every few seconds and nothing renders it. Scroll position is deliberately absent — read markers already record it
- The composer is a contenteditable div, so its value is a DOM tree and a message is a string. `lib/composer.ts` holds that conversion; `getComposerText` and `setComposerText` must stay exact inverses, since a draft round-trips through them between devices
- Sounds (`backend/sounds.rs`, `lib/sounds.ts`): a room ships a pack replacing the built-in effects (`PACK_EVENTS` / `SoundEvent` — keep the two lists in sync), and a member can set a short entrance sting played when they join a voice channel. Every effect goes through `playSound`, which resolves the room's override then the built-in and applies the listener's own volume; `voice-leave` has no file of its own and is the join sound reversed at runtime, so `resolveSound` answers `null` for it. On the web every effect plays through one long-lived AudioContext (`lib/sounds.ts`): made on the first click so a socket-triggered sound never has to start it, resumed on focus, routed to the voice output device, playing buffers decoded ahead of time — the built-ins at load, rooms' packs when rooms load (`host.prewarmSounds(urls)`), anything else (a sting) after its first play, which falls back to an `<audio>` element. A sound is dropped rather than queued on a context that will not run, or it goes off whenever the context next wakes. `stream-start` plays to everyone in a call when a screen share or webcam starts in it, off the server's echo — except a screen sharer's own, which `useWebRTCScreen` plays when the publisher connects (the desktop app's native capture is still starting when the echo lands, and swallowed it);  Its built-in file is CC BY 4.0 and credited in the README — any shipped effect with an attribution licence needs the same
- A chosen sound is length-checked server-side with ffprobe when it is *set*, never trusted from the client — it plays without anyone asking for it. Only `/external/...` files this instance hosts are allowed. The sting travels with the `voice_user_joined` broadcast, and is empty when the room has entrance sounds off, so a client never decides whether to play one
- Idle is about the person, not the socket. `presence_status` has always computed it correctly from `last_active`, but `handle_ws_text` refreshed that field for *every* message and the client sent a keepalive every minute — so nobody was ever idle and the status, though rendered, could not happen. `marks_user_active` now excludes the traffic a client generates on its own (the keepalive, a resync after a tab wakes, all `*_webrtc_*` negotiation), as a denylist so a new *user* action counts without anyone updating it. The client sends `activity` in place of the keepalive: at most once a minute, only when there has been real input since the last one, and never from a hidden tab. The socket's own ping/pong is what proves the connection is alive, so nothing was lost by making the app-level message mean something
- Going idle is the only presence transition with no event behind it — it is the absence of one — so `presence_sweeper` in `app.rs` is what announces it, every `PRESENCE_SWEEP_SECS`. It also refreshes `last_active` for anyone sitting in a voice channel, because being in a call is being present whether or not anyone is talking; doing it by refreshing the record rather than special-casing the status keeps the REST endpoint and the pollers agreeing without any of them knowing about voice
- A dropped socket leaves a hole in presence as much as in the timeline: a status that changed while it was down was broadcast to nobody, and the ten-second poll only covers the room on screen and only once it next fires. `recoverMissedMessages` therefore refetches presence alongside the voice snapshot and the unread counts, and the tab-resume path does the same
- Themes have two authorities and they do not overlap. A **built-in** is the hand-authored oklch block in `index.css`, and `resolveThemeColors` reads its colours back out with a hidden probe element rather than keeping a second copy in TypeScript — which is why `index.css` aliases `:root`/`.dark` to `[data-theme="light"]`/`[data-theme="dark"]`: matching a rule on the probe is what stops it inheriting the applied theme from `<html>`. A **custom** theme is four colours plus optional overrides, and `deriveThemeVars` turns those into the same variables. It deliberately leaves `--destructive`/`--success`/`--warning`/`--info` unset so they fall through to the base block the theme's `mode` selects
- A theme id reaches a CSS attribute selector (`html[data-theme="..."]`), so it is constrained to `[A-Za-z0-9_-]` on write (`helpers::valid_theme_share_code`, `appearance.rs`) and again wherever one arrives from storage or the network (`isSafeThemeId`). Colours are `#rrggbb` on both sides for the same reason
- Appearance settings sync per user through `GET`/`PUT /api/appearance`. `ThemeSync` pushes nothing until the first fetch answers — a device that pushed first would overwrite the account's settings with the defaults it started on — and `index.html` replays a localStorage cache of the applied theme before first paint, deriving nothing
- A room suggests a theme as a `ct1_` share code on `m.room.theme`, gated by `manage_channels` like the sound pack. It is a suggestion: the client offers it once per code and applies nothing on its own
- A **profile** theme is a different thing from the app theme and shares none of its machinery. The app theme is the viewer's choice about their own client and covers every surface; a profile theme belongs to the person, is set by them, and reaches exactly two places — their profile modal and their tab in the member list. It is `profile_theme` on the user record, a `{ modal, tab }` pair of `{ color, color2, fade, direction }`, riding along with presence like `name_font_url` does so a member tab already has it without a second fetch. The two surfaces are set **separately** and neither derives from the other: a card with room for a gradient and a strip beside dozens of others rarely want the same thing, which is also why the alpha they are laid on at differs (`PROFILE_WASH_ALPHA`)
- `lib/profileTheme.ts` is the single definition of what those fields mean, so the tab and the modal cannot drift: the first colour holds for `100 - fade` percent and turns into the second over the rest, so fade 0 is a solid even wash and fade 100 spreads the change over the whole surface. `color2` empty is a *different look*, not an absent one — the colour fades into itself at zero alpha, which lets the wash blend into the card. Never fade to `transparent`: that is transparent **black** and greys the middle of the gradient
- The colours reach a CSS gradient on every client that draws the person, so they are `#rrggbb` on both sides (`helpers::valid_profile_color`, `readProfileTheme`) and the direction is a closed set of four. The theme arrives whole and is parsed whole (`parse_profile_theme`): a bad **colour** sinks the entire theme rather than being dropped from it, because a half-applied one leaves someone looking at something they did not choose, while a stray fade or direction is absorbed — the editor cannot produce either. The profile banner is *masked* rather than covered by a fade-to-background overlay: an opaque overlay paints over the wash behind it and leaves a seam where the banner ends
- The **accent** is that theme's third job and is *derived*, never set: `profileAccent` takes the member-list tab's colour, falling back to the card's. It is the person's mark everywhere outside their profile — the ring and name while they speak (`speakingStyle` replaces the uniform `--success` at all three voice surfaces), their dot in the typing indicator, and the tint under their messages on hover (`.msg-sender-accent` reads `--sender-accent` off the row; a mention keeps `.msg-mentioned`, since being named outranks who said it). A fourth control for "and your colour everywhere" would be a fourth thing to keep in step with the other three
- The sidebar's top level — folders and the rooms outside them — is arranged by `lib/sidebarOrder.ts` from one stored list of ids, saved per user on the `room_groups` record (`order`) so it follows them to every machine they sign in from. One list rather than a position on each, because a folder sits *between* two rooms, which two orderings cannot express. It is partial on purpose: an id it does not name falls to the end in the order it always had (folders by `position`, then rooms as the app lists them), so joining a room needs nothing rewritten and a user who has never dragged anything sees what they saw before. `PUT /api/room-groups/order` cleans what the client sends (an id twice is a room drawn twice) and renumbers group `position` to agree, since that field predates the list and anything still reading it has to see the same arrangement
- The rail and the expanded list draw from that same arrangement, so neither can disagree about where a room is. Every icon on the rail is one square, `--rail-icon`, declared once on the rail's container and never restated — the pills and the folder wash are `calc()` off it, so the whole column moves together. On the rail a folder is one such icon: closed it shows a 2x2 of its first four room icons and carries their unread state, because a badge on a room nobody can see is a badge nobody can see; open it shows a folder glyph and its rooms stack under it on one soft wash — the wash runs behind the folder icon *and* its rooms and is wider than they are (the icon square plus 0.75rem), because a strip that starts below the icon and matches its width draws a folder and then some rooms rather than a folder of rooms. The wash — and the folder icon, drawn in the same colour so an open folder is one unbroken shape — is `--muted`, which is what the page itself is painted in behind every panel (`ChatLayout`'s root). A folder therefore reads as a hole cut through the rail onto the page, in whatever hue the theme's backdrop carries. The colours it is *not*: the accent (`sidebar-primary`) puts a second colour on a rail that already draws the active room in it; an alpha of `sidebar-foreground` is neutral by construction and comes out grey whatever the theme; `--background` is the *chat* surface, a different colour from the page behind the panels. `--muted` equals `--sidebar-accent` under most themes, which is what idle room icons are drawn in — so a room **inside** an open folder is drawn on `--sidebar` instead, or it is a letter floating on the wash with no disc under it. Open/closed is the group's `collapsed` field — the same one the expanded list toggles — so a folder opened on the rail is open everywhere that user is signed in. The middle of a folder icon is "drop inside", its top and bottom quarters are "drop beside": without the edges a folder could be dropped on but never moved past. A room keeps its id in the order while it sits in a folder (a grouped id is ignored when arranging), which is what puts it back in its old slot when it is dragged out rather than at the end of the rail
- The channel column measures itself to its longest row per room (`measurePanelWidth`) until the reader drags the handle, and a dragged width then wins for **every** room. That width cannot live in the component: selecting a room empties `channels`, the layout drops the column while it has nothing to show, and what comes back is a new component measuring the new room — so a dragged width lasted exactly as long as the room it was set in. `lib/channelPanelWidth.ts` holds it, in localStorage and behind a read-once cache, and `null` there means "never dragged", which is what keeps the per-room measuring for anyone who has not touched the handle. Per browser rather than per account, like the screen share ceiling: a column width is about the window it is in
