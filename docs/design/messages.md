# Messages, threads, pins and links

How messages are sent, paged, linked, pinned, deleted and threaded, and how a dropped socket is repaired. Read before changing message routes, the timeline, threads or pins (server or client).

Moved verbatim from the root AGENTS.md; keep it current when you change the behaviour it describes.

- Auth endpoints: POST `/_matrix/client/r0/register`, `/login`, `/logout`
- Room CRUD: POST `/createRoom`, `/{room_id}/join`, `/{room_id}/leave`; GET `/joined_rooms`
- Messages: PUT `/{room_id}/send/m.room.message/{txn_id}`; DELETE via `/{room_id}/redact/{event_id}/{txn_id}`
- Reactions: PUT `/{room_id}/send/m.reaction/{event_id}` (toggles on/off)
- Pins: GET `/api/rooms/{room_id}/pins?channel_id=` (or `?thread_id=` for a thread's own pins); POST/DELETE `/api/rooms/{room_id}/pins/{event_id}` (owner/moderator, a `manage_messages` role, or any DM member)
- **Channel links** (`packages/core/src/channelLinks.ts`): typing `#name` in the web's channel or thread composer offers the room's channels in the mention menu, and on send every `#name` naming a channel the sender can see becomes `<#channel_id>` (longest name wins, so names with spaces work; fenced code is left alone; editing decodes and re-encodes). The body carries the **id**, never the name: a rename reaches every old link, and a private channel's name is not written into a channel whose members may not know it exists. Each reader resolves it against the channels *they* can see (`visibleChannels`) — `#name`, clickable unless it is a voice channel, or `#unknown` — on the web (`MessageItem`), on mobile (the `channel` node of `parseInline`), in previews (`plainText`/`plainChannelLinks`) and in push, per recipient (`render_channel_links` in `push.rs`; keep its regex in step with `CHANNEL_LINK`). That holds because `GET /rooms/{id}/channels` lists only channels the caller can view. A link shown outside its room (activity page, a notification from another room) reads `#unknown`, since only the open room's channels are held
- Shared message links (`backend/routes/message_links.rs`, `lib/messageLinks.ts`) are `/m/{event_id}` and carry nothing else — not the room, not the channel, not the message. `GET /api/messages/{event_id}/preview` resolves one **per viewer**, which is the whole design: permission to read a channel belongs to the person looking, so an unfurl baked into the sharing message would be private content sitting in a channel whose members were never allowed to see it. Every refusal — no such event, not a member, no channel access, a thread reply, redacted — answers the same 404, so holding a link reveals nothing; the client draws an inert "Message unavailable" instead of a card. The URL itself is suppressed from the body (the card replaces it and carries a copy button), which is *why* that placeholder exists: a message whose whole content was a link would otherwise render as an empty bubble. `MessageLinkEmbed` keeps three states apart, not two — unresolved and a retryable failure both render nothing, and only the server's 404 draws the placeholder, so a dropped connection is never reported as "unavailable". `/m/{event_id}` serves the bare client with **no** OG meta tags, unlike `/invite/{code}`: those are served without a token, so a message in them would publish a private channel to anything that unfurls links. Resolutions are cached client-side (5 min, refusals included) and dropped on the edit/redaction broadcasts and on sign-out
- Paged listings (pins, search, threads) take `limit`/`offset` and answer with `{ items, has_more, next_offset }`; page with `next_offset`, not the row count
- Messages are the exception: they page by **keyset**, not offset. `before_ts`+`before_event_id` scroll back, `after_ts`+`after_event_id` close a gap, `around_ts` centres on an anchor; all fetch `limit + 1` so `has_more` needs no count. The cursor is the *pair* because `origin_server_ts` is milliseconds and collides — a timestamp-only cursor skips or repeats messages sharing one. Combine a cursor with the visibility filter through `and_filter`, never by merging keys: the base filter has its own `$or` for channel access and a second one would replace it
- A thread's replies page the same way (`GET /api/rooms/{id}/threads/{root}` with `limit`/`before_ts`/`before_event_id`, answering `has_more`): the panel opens on the newest page at the bottom and prepends older pages as the reader scrolls up, holding the top reply in place. Since the client holds only the pages it has loaded, anything that used to be counted off them comes from the server instead — the first page puts `thread_reply_count` on the root and lists every `posters`. A pin or a quoted reply older than what is loaded is reached through `revealThreadMessage`, which pages back until it finds it
- Pin changes broadcast `m.room.pinned` / `m.room.unpinned` to the room
- A dropped socket leaves a hole: live events are the only thing that puts a message into an open channel. `ws.onopen` therefore treats every connection after the first as a repair, calling `recoverMissedMessages`, which replays from the newest message actually held via `after_ts` and reloads the server-computed unread counts. `after_ts` on `GET /rooms/{id}/messages` is a timestamp range, not an offset page, and its `has_more` means "the gap was wider than one page — ask again from the last message you got"
- Threads are records in `threads` (`ThreadRecord`), written where a thread changes — a reply upserts one, bumping `last_activity_ts`, the reply count and the participants. Listings read that, never the messages: `GET /api/rooms/{id}/threads` takes `active_within_ms` and sorts by last activity, which is *not* the root message's timestamp. Both thread paths gate on `channel_permissions`, so a thread is exactly as private as its channel
- A thread reply carries no `channel_id`, so a visibility filter of "allowed channels, or no channel" admits every reply in the room, private channels included. Anything listing messages across channels for a restricted member — search, the activity page, sync — builds its `$or` from `helpers::visible_message_arms`, which admits a channel-less message only when it is not a reply, and a reply only when its thread is in `visible_thread_ids` (threads whose root is in an allowed channel)
- A reply count means **replies that are not deleted**, and three places computed it: `ThreadRecord.reply_count` (the thread list), `get_thread_counts_for_events` (the badge on a root message), and the count a reply broadcasts. A redaction keeps the row and marks it, so the two live counts counted deletions, and the stored one had never had anything taken off it at all. All three exclude `redacted` now, and `redact_message` recounts the thread and `$set`s the record — recounted rather than decremented, so a count that had already drifted is corrected instead of carried forward one lower
- The redaction broadcast carries `thread_id` and `thread_reply_count` when the deleted message was a reply, because a deletion is the one thing that changes a count without a reply. `UPDATE_THREAD_REPLY_COUNT` updates both places the number is shown — the badge and the channel list's preview row — while `THREAD_ACTIVITY`, which re-sorts by timestamp, stays for replies only: losing a reply is not activity and must not lift the thread up the list
- A thread reply reaches its participants and anyone named, in the page and via push (`MessageNotification.audience` narrows delivery before policy runs). It does not reach the whole room — a thread is a side conversation. Thread replies carry no `channel_id`, so unread counts exclude `thread_id` or they land in the channel-less bucket
- A thread has its own composer and so its own reply target, `state.threadReplyingTo`, separate from the channel's `replyingTo`: `MessageItem` rendered `inThread` sets that one. Sharing the field put a thread message's quote on the *channel's* composer, and `send_thread_message` ignored `in_reply_to` anyway. The server only quotes a parent **inside that thread** (its root or one of its replies, via `quote_parent`) and drops anything else, since a quote would carry another channel's text into the thread; whoever is answered joins the participants, which is how the root's author hears a reply to them
- A thread's pins are its own list: `PinRecord.thread_id` is set for a pinned thread reply, `GET .../pins?thread_id=` lists them, and every channel pin query filters `thread_id: null` (absent on older records) so they never show in the channel. The record still carries the root's `channel_id`, so channel access is judged the same way and deleting the channel takes them with it; `delete_thread` clears them. `m.room.pinned` carries `thread_id` and the client routes it to `state.threadPins`, fetched in `openThread`; an unpin names only the message, so `REMOVE_PINNED_MESSAGE` clears it from both lists
- The channel list previews up to `THREAD_PREVIEW_LIMIT` threads per channel from the last `THREAD_ACTIVE_WINDOW_MS`, updated live from the `m.thread.message` broadcast. An unnamed thread's row is the message that *started* it, on load and live alike — the broadcast carries `thread_root_body` for that, since its `content` is the reply and a thread's first reply is the first the list hears of it. It is a recency preview, not an inbox: a thread dropping off must never take an unread mention with it, which is why the notification and the room badge carry that instead
- A row that stands for a *message* but lives outside its room — the activity page's room list — opens the room **on that message** through `openMessage`, not `selectRoom`. The two halves cannot sit in one place: landing on a message needs the room's channels and timeline, which exist only after selecting the room has finished, and the row that asked is unmounted by that very switch. So the target (room, channel, event, timestamp) goes into `state.pendingJump` and `ChatArea` acts on it once `currentChannelId` is set, switching channel if the message is in another one and fetching a page centred on it. `SELECT_ROOM` keeps a pending jump only when it names the room being opened — any other target belongs to a room the switch walked away from and would fire the next time that room came up. `ChatArea` guards on the target's *identity*, so the same row clicked twice jumps twice
- A delete is broadcast the moment the message row is updated, before the pin removal and the attachment purge. The purge scans the message collection for other uses of each file, which is seconds on a busy room — broadcasting after it left a deleted message on every screen in the room, including the screen of the person who had just deleted it. It is spawned rather than awaited: nothing in the response depends on it
- `deleteMessage` also dispatches `REDACT_MESSAGE` against the successful `DELETE`, so the deleter's own client does not depend on the socket for news it already has. `REDACT_MESSAGE`/`REMOVE_MESSAGE` remove by filtering and so are safe to apply twice, which is what makes that and the broadcast able to coexist. They clear the timeline, the pin list **and** an open thread — a message is on screen in up to three places, and deleting a thread's root closes the thread rather than leaving replies to something gone
- WebSocket messages use a `type` field: `typing`, `voice_join`, `voice_leave`, `voice_mute`, `voice_deafen`, `voice_state_request`, `screen_share_start`, `screen_share_stop`
- WebRTC signaling for voice and screen share flows through the WebSocket
