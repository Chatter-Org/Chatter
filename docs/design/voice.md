# Voice, screen share and spatial channels

Voice state authority, signalling order, SFU slot forwarding, mute/deafen, TURN, spatial floor, clips. Read before changing ws voice handling, webrtc.rs, the shared VoiceEngine or voice UI.

Moved verbatim from the root AGENTS.md; keep it current when you change the behaviour it describes.

- Mute and deafen belong to the person, not the channel: `joinVoice` preserves both when it is entered while already in a call — a rejoin or a channel switch — silences the fresh track before publishing, and sends them **on the `voice_join` itself** (`muted`/`deafened`), which the server writes into the member record as it registers the arrival. They used to follow the join as two more messages, and each was a second broadcast, so the room saw an open mic on someone who arrived muted and was corrected a moment later. A server mute still wins: `force_muted || joined_muted`
- A dropped socket also ends the call: the server tears voice state down on disconnect, so `ChatLayout` re-issues the join on a *re*-connection when the client still believes it is in a channel. The older sessionStorage rejoin beside it only ever covered a page refresh — it is one-shot per mount and consumes its key on read, so a socket blip reached it never
- A voice stream's cost is mostly headers, not Opus: at the 32 kbps default a 20 ms packet is 80 bytes of payload under ~50 of IP/UDP/RTP/SRTP, and the packet *rate* is what the SFU spends its CPU on — once per listener, not once per speaker. So publishers are asked for 40 ms frames (`VOICE_PTIME_MS`), which halves the packet rate and takes about a fifth off the bandwidth for 20 ms of added latency. For Opus it is the **receiver's** SDP that tells an encoder what to send, and `ptime`/`maxptime` are media-level attributes rather than fmtp parameters, so `mungeVoiceAudioSdp` writes them into the SFU's *answer* before `setRemoteDescription` — the server never negotiates it. `OPUS_FRAME_SAMPLES` is derived from `VOICE_PTIME_MS` rather than written out so the two cannot drift; it is only the fallback advance for a slot handover, so a publisher that ignores the request costs one packet of timestamp skew on a packet that carries the marker bit anyway
- A slot's output clock follows **wall time** wherever the input's cannot be trusted — a new run after a handover, or a timestamp jump past `VOICE_MAX_TS_DELTA` (`restamp`, `SlotRestamp.last_out`). It used to advance one frame there, which told the listener's jitter buffer that audio seconds apart was contiguous; it read the gap as jitter, grew its delay and time-stretched back down, so every speaker change started choppy. A forwarder also survives a failed `write_rtp`: it used to stop on the first one while its assignment stayed put, and since the sweep never moves a speaker who is still wanted, one transient send error silenced that speaker for that listener for the rest of the call. Teardown and reassignment abort the task, so it cannot outlive its slot
- Voice signalling tolerates ordering. The SFU trickles candidates that can overtake the answer, and a candidate added before the remote description is rejected — so `lib/webrtc.ts` holds them per connection (`holdCandidatesUntilAnswer` / `releaseHeldCandidates`) and whether a call connected no longer depends on which message the server sent first. Both connections are rebuilt when they stall: no answer or no connection within `VOICE_CONNECT_TIMEOUT_MS`, or `disconnected` past `VOICE_DISCONNECTED_GRACE_MS` (a browser only reaches `failed` after ICE consent runs out, around thirty seconds of silence). A connection that broke is retried for the whole call on a backoff; one that never got an answer is capped, and a publish refused with `code` `force_muted`/`cannot_speak` is not retried at all
- The playout `AudioContext` is resumed on the next gesture and whenever the tab becomes visible (`keepRunning` in `browserVoice.ts`). One built without a gesture — a refresh rejoining the call, a rebuilt subscription — starts suspended, and iOS suspends it on an interruption, so those people heard nothing at all
- TURN addresses handed to browsers come from `client_turn_urls`: an internal-only host (`host.docker.internal`, a bare service name, loopback) is replaced by the host the client reached the server on (`SERVER_URL`, else `X-Forwarded-Host`/`Host`), and every bare `turn:` URL is paired with its `?transport=tcp` twin. The compose default used to reach clients verbatim, so the relay was unreachable for exactly the people who needed it, and with no TCP path a network that blocks UDP could not connect at all — the SFU has no ICE-TCP of its own
- The slot forwarder is the hottest loop in the server — it runs once per packet *per listener* — so it builds its outgoing packet rather than cloning and editing one. Every publisher packet carries the audio-level extension, so `packet.clone()` allocated an extension vector only for the next lines to empty it. `payload` is `Bytes`; carrying it over is a refcount bump. Note `write_rtp` clones again internally and overwrites `ssrc`/`payload_type` per binding, so that second clone is cheap only because the extensions are already gone
- Voice state has one shape and one authority. `voice_channels` on the server is the whole truth, and every event that changes it — join, leave, moderation, a disconnect — carries `voice_states`: the full record (`muted`, `deafened`, `screen_sharing`, `force_muted`, `clipping`) of *everyone left in the channel*, not just the ids. A client replaces the channel outright from that, so one it had never seen is right immediately instead of being invented unmuted
- Voice moderation is one socket frame, `voice_moderate` (`action`: `mute` | `unmute` | `move` | `disconnect`), owners and moderators only, never on yourself, and a moderator never on the owner. It acts only on a session in a channel of the frame's `room_id` (the member record's `room_id`), and a move's `target_channel_id` must be a voice or spatial channel of that room: it once searched every channel on the server, so owning any room the target was in was enough to cut their call in another. The target is sent `voice_force_muted`, `voice_force_moved` or `voice_force_disconnected`; the engine says "A moderator disconnected you from voice" on the last. `moderateVoice` is a core store action; the web puts it behind the shield on a voice member, the Android app behind the shield on a channel's occupant, which opens a sheet
- A voice event describes a change, so one sent while a socket was down reaches nobody and leaves that client wrong with nothing to notice it by. `voice_state_snapshot` answers that: every occupied channel in every room the user belongs to, keyed by channel with its `room_id` and `occupied_since`. It is pushed unasked right after the `connected` ack, and sent again to the one connection that asks with `voice_state_request` — which the client does on opening a room, on coming back from a backgrounded tab, and as `loadVoiceMembers` whenever a socket is open. `GET /api/rooms/{id}/voice` remains the fallback for when one is not, and covers a single room, so a snapshot built from it is applied **scoped to that room** (`SYNC_VOICE_STATE.roomId`) — reading its silence about the others as "empty" would end calls it was never asked about
- Client-side, `voiceChannelMembers` is global, not scoped to the room on screen: a call in another room still has a sidebar row and a DM bar, and your own call keeps its panel while you read elsewhere. `SELECT_ROOM` therefore does not clear it. Everything flat is *derived* from it in the reducer (`deriveRoomVoice`, `withRoomVoiceCounts`) — `voiceMembers`, `voiceMemberStates`, `activeScreenSharers`, and the per-room head-counts the sidebar shows — for the room the client is in a call with, else the one on screen. Two structures maintained side by side from different events is why the member list and the channel list could disagree about who was muted
- A **spatial** channel is a voice channel with a floor, and deliberately adds no second system: the same `voice_join`, the same SFU, the same `connect` permission. The only new state is where each person is standing, and it lives *on `VoiceMemberState`* rather than in a map beside it — so the five paths that already end a membership already forget the position, and every event that carries `voice_states` already carries it, snapshot and REST fallback included. Both axes are 0..1 so no two layers have to agree on a pixel size. A first arrival is placed on a ring by `spawn_position`, whose angle comes from the user id: everyone landing on one point means everyone landing inaudibly loud on top of each other, and a hash rather than a counter means the same person reappears where the room last saw them
- Moving is `voice_move`, answered by a `voice_position` broadcast carrying **one** person rather than the whole channel — the exception to the rule above, because at drag rate the full record every frame is what would actually cost. A dropped one is a stale dot until the next move or the next join/leave/mute, all of which still carry everything. The client meters to ~16/s with a *trailing* send (a plain throttle loses the last frame, which is the one that says where you stopped) and the server meters again with `ratelimit::VOICE_MOVE`, **dropping** refusals rather than reporting them: the next position supersedes the last, so an error per frame would be worse than the flood
- The hearing is entirely client-side and the server never learns who can hear whom — the SFU forwards rather than mixes, so every listener already has each speaker on their own slot. `useWebRTCVoice` therefore inserts a `PannerNode` after each slot's gain, and re-aims it when the slot changes hands instead of rebuilding it, because rebuilding drops the audio mid-word. The panner is built for **every** call, spatial or not: at the listener's own position it is inert, and adding one mid-call would mean rewiring under a live stream. `lib/spatialAudio.ts` is the one definition of the geometry, so the floor and the ears cannot disagree; screen y maps to audio **z**, since the floor is seen from above. Never fade a panner to `transparent`-style silence at the edge — the distance model deliberately bottoms out audible, or the far half of the floor is unusable
- A **clip** of a screen share is captured the moment it is taken and then offered to a channel the clipper picks (`ClipChannelDialog`), in the *call's* room rather than the room on screen. The list comes from `GET /api/rooms/{room_id}/postable-channels`, which runs the checks `send_message` runs — room `send_messages`/`attach_files`, `read_only` on room and channel, and the channel's overwrites for `view_channel`/`send_messages`/`attach_files` — so it never offers a channel that would refuse the post. Change one alongside the other. The upload waits for the choice, so a discarded clip leaves nothing on the server
- A **DM call** has cameras like any voice channel: the camera button in `DMCallBar`, a "See camera" way in per person, and "Start a video call" in the DM header, which joins and opens the camera picker once the call is up (`videoCallPendingRef` in `ChatLayout`, forgotten after `VIDEO_CALL_JOIN_WAIT_MS`). Camera frames name the **call's** room (`callRoomId` in `useWebRTCWebcam`), not the room on screen — the start/stop broadcast goes to whichever room the frame names, so a camera turned on from the voice bar while reading elsewhere used to be announced to the wrong room
- The viewer has two layouts. With two or more feeds and none picked (`selectedScreenSharer` and `selectedWebcamStreamer` both null) it is a **grid** of every screen and camera; picking a tile focuses it, and the strip's Grid button (`SET_SCREEN_VIEWER {sharer: null}`, which clears both) goes back. The column count comes from `gridLayout` in `packages/core/src/voice/grid.ts`, which tries each and keeps the one with the largest 16:9 tile for the panel's measured size — so two feeds sit side by side on a monitor and stack on an upright phone. A camera tile gets a ring while its owner speaks, sampled from `speakingUsersRef`. In the grid a screen tile is the only element playing that share's sound, so it is unmuted at the sharer's volume. A selected camera that has gone off counts as no selection
- **Background blur** is done in the sender's browser (`client/src/lib/backgroundBlur.ts`); the SFU forwards the result like any camera. MediaPipe's selfie segmenter gives a per-pixel person mask; the frame is drawn through it over a copy blurred at a quarter size and stretched back up (a full-size blur was most of a frame's cost). The WASM runtime and model come from this server's hashed `/assets` via `?url` imports, never a CDN, and the module is only loaded by dynamic import the first time blur is turned on. Chromium (and so the desktop app) reads camera frames with `MediaStreamTrackProcessor` and writes blurred ones to a `MediaStreamTrackGenerator`, which does not depend on the page painting — a canvas `captureStream`, even with `requestFrame()`, only hands frames over on a repaint, so it froze whenever the sender's tab was hidden. Firefox and Safari fall back to the canvas stream on a worker's clock and can still stall in a hidden tab. Blur sends at 30 fps; the camera picker previews it and remembers the choice per device (`chatter_camera_blur`). A blur that fails to load leaves the camera on without it and says so
- With the UDP mux (one socket for every peer connection, `WEBRTC_UDP_PORT`), ICE is restricted to **IPv4** (`set_network_types([Udp4])`). The socket is IPv4, and every local candidate on the mux reads from one shared connection: whichever reads a packet looks its sender up among the remote candidates of its *own* network type, so an IPv6 host candidate (a link-local fe80 address is enough) discarded the IPv4 packets it happened to read — 13–45% of inbound media on such a host, which browsers took for congestion and answered by cutting their bitrate to the floor. Note also that webrtc-ice gathers no server-reflexive candidates on a muxed connection, so `WEBRTC_IP`'s srflx candidates are not advertised while the mux is in use; remote clients reach the server through TURN
