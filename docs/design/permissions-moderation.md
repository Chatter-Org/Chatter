# Permissions, moderation and admin

Role hierarchy, channel overwrites, effective permissions, rate limits, audit log, blocking, timeouts, the rules gate, reports, bulk deletion, automod, invite limits, admin metrics and export. Read before changing any access check, moderation tool or admin route.

Moved verbatim from the root AGENTS.md; keep it current when you change the behaviour it describes.

- Anything user-supplied that reaches a `$regex` goes through `helpers::regex_escape` first — unescaped it both mismatches (`a.b` matching `axb`) and lets a crafted pattern backtrack over a whole room
- Role hierarchy: **lower `position` = higher authority** (owner, then moderator, then custom roles top-down). `role_authority()` ranks a user, `outranks_role()` gates editing/deleting/assigning, and `ungrantable_permission()` stops anyone handing out a permission they do not hold
- Channel overwrites: `channel_permissions()` layers the category's `overwrites` then the channel's over the room set — everyone, then the union of the member's roles, then the member; denies before allows in each step. Owners and moderators bypass them. Legacy `view_roles`/`write_roles` are folded into overwrites by a one-time startup migration (`overwrites_migrated`)
- Permissions: every access check goes through `effective_permissions()` in `helpers.rs`. Owner holds all, moderator holds a fixed legacy set, both keep what their custom roles add; a member with no custom roles gets `RolePermissions::default()`, and once they hold roles the union of those roles is authoritative. `GET /api/rooms/{room_id}/permissions` returns the caller's own set — the client mirrors it only to hide controls
- Rate limits live in `backend/ratelimit.rs` as token buckets (burst then meter, so pasting three messages is fine and a loop is not), keyed `"<bucket>:<who>"` in an ephemeral `AppState.rate_limits`. Slowmode is the same mechanism with capacity 1 and the channel's period, bypassed by `can_manage_messages` like `read_only`. Refusals go through `helpers::rate_limited`, which always includes `retry_after_secs` — a limit that only says "no" reads as a bug. Registration carries a second instance-wide bucket because the per-address one reads `X-Forwarded-For`, which is only trustworthy behind a proxy
- Moderation is logged: `backend/audit.rs` appends to `audit_log`, read back by owners/moderators at `GET /api/rooms/{room_id}/audit` (paged, `action` filters by prefix — "member" matches every `member.*`). Entries are append-only with no edit or delete route: a log a moderator can rewrite is not a log. `record()` is best effort and its result is ignored on purpose — an action that succeeded must not report failure because the log write did. Details name *which fields changed*, never message bodies; deleting your own message is not logged, only a moderator deleting someone else's
- Server metrics (`backend/metrics.rs`, `GET /api/admin/metrics`, admin only) exist for one question: how much the media plane actually costs. The RTP forwarders count ingress once per publisher packet and egress once per *subscriber* write, using the byte count `write_rtp` reports, so a paused sender adds nothing — the number is egress, not the bitrate the client was configured for. Counters are cumulative and the endpoint computes no rates: the dashboard polls and diffs against `timestamp_ms`, because a window kept server-side is one every later caller has to agree with, and an average hides the spike that saturated the link. The counters live in a global rather than `AppState` because the forwarding tasks are spawned closures that capture only a track and a channel. `media_job()` gauges the ffmpeg passes, which are uncapped and compete for the same cores as forwarding
- `GET /api/admin/export` streams a full logical backup as NDJSON (`{collection, doc}` per line) through an mpsc channel, admin only. It **includes password hashes, TOTP secrets and recovery codes** — a backup that cannot restore logins is not one — and excludes `refresh_tokens`, which would resurrect dead sessions. Uploaded media is not in it; `external/` must be copied alongside
- Blocking is enforced through `helpers::is_blocked_between`, which checks **both** directions — opening a DM, creating or being added to a group DM, and sending into an existing DM. It lived only in `friends.rs` before, so "Block" stopped friend requests and nothing else
- **Timeouts and the rules gate** (`backend/moderation.rs`) are not checks of their own: `effective_permissions` and `channel_permissions` switch off `send_messages`, `attach_files`, `add_reactions`, `connect` and `speak` for a restricted member, applied *after* channel overwrites so no allow undoes them. That is what makes every existing check — forum excepted, see below — enforce them. `participation_refusal` gives the same answer with a reason (`code: timed_out | rules_pending`) for the handlers where the person should be told why: sending, thread replies, reactions, edits. Forum writes are not gated on `send_messages` at all, so `forum.rs` asks `participation_refusal` itself
- A timeout is a `member_timeouts` record keyed `{room_id}:{user_id}` (epoch ms; one in the past is none, so nothing clears it when it ends). Not a field on `room_members`: leaving deletes that record, so a timeout kept there was escaped by leaving and rejoining. Set with `PUT/DELETE /api/rooms/{id}/members/{user}/timeout`, which takes `kick_members` and the same hierarchy as kicking (`may_act_on`): not the owner, not yourself, moderators not on moderators. 1 minute to 28 days. It cuts a voice publisher already running in the room; new ones are refused at the publish path by `speak`. Broadcast as `m.room.member.timeout`; the member list carries `timeout_until`. The client refetches permissions when a timeout is due to end — the server announces nothing then
- The rules gate holds a member until `room_members.rules_accepted_at` is set (`POST /api/rooms/{id}/rules/accept`). It is in force only when the owner has turned it on **and** written rules (`rules_gate_active`), never holds owners or moderators, and is passed once: rewording the rules does not send everyone back through it. `GET /api/rooms/{id}/permissions` answers `restriction: {timeout_until, rules_pending}` beside the permissions, which is what the composer words itself from
- Moderation settings live on the room (`RoomRecord.moderation`) and only the owner changes them (`PUT /api/rooms/{id}/moderation`). Members see `moderation::public_view` — rules, whether the gate is on, whether reports are — in sync (`m.room.moderation`) and in the broadcast when it changes. The automod word list is moderators-only: publishing it hands out the list of what to misspell
- Reports (`reports` collection) keep a copy of the message as it read when reported, so the author deleting or editing it does not stop a moderator judging it; the copy is moderators-only and is deleted with the room. One open report per reporter per message (reporting again replaces the reason). Reviewers are the owner, moderators, and anyone with a custom role granting `manage_messages`, `kick_members` or `ban_members`; they are sent `m.room.reports` with the open count. Closing one report closes every open report of the same message. `reports_enabled` turns the whole thing off
- Deleting a message goes through `messages::perform_redaction`, whether one at a time, from a report, or in bulk, so a message is gone the same way each time. Bulk deletion (`POST /api/rooms/{id}/messages/bulk-delete`, `manage_messages`) takes one person's messages from the last hour to week, at most 1000, skipping `m.system` notices. It works on someone who has left or been banned — that is when it is wanted — and applies the hierarchy only while they are still a member
- Automod runs last in the send path, on edits, thread replies and forum writes, after every plainer refusal, so a message refused for another reason is not also logged as tripping a filter. Anyone with `manage_messages` is exempt, as are bots. Blocked words match as whole words after normalising (lowercase, punctuation as spaces); a trailing `*` matches a prefix. Repeats are checked against the sender's messages in the last minute, and not on edits. Each block is audited as `automod.blocked` naming the filter, never the words; with `timeout_secs` set the sender is also timed out, with `automod` as the actor
- Invites can be limited to `max_uses`. A use is a join, not a click: it is claimed with one conditional `$inc` before joining (so two people cannot both take the last one) and given back if the join is refused. A member using the link again is let in without spending one
