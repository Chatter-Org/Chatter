# Notifications, push and unreads

The two halves of notification (connected client vs Web Push), unread buckets, mentions and read-marker sync across devices. Read before changing push.rs, webpush.rs, read_markers.rs, lib/notifications.ts or unread state.

Moved verbatim from the root AGENTS.md; keep it current when you change the behaviour it describes.

- Notifications have two halves that never overlap. A **connected** client raises its own from the WebSocket event (`lib/notifications.ts`); a member with **no** socket is reached by Web Push (`backend/push.rs`), which is why `deliver_message` skips anyone in `active_websockets`. The level rules are ported into `backend/push.rs` from `lib/notifications.ts` — change both together. The wire protocol (RFC 8188/8291/8292) is in `backend/webpush.rs`, verified against the RFC 8291 test vector; it is hand-rolled because the `web-push` crate pulls OpenSSL through `ece`
- Push covers every path that broadcasts `m.room.message` — `send_message` and `execute_webhook`. Thread replies broadcast `m.thread.message`, which neither half notifies on
- A push subscription is bound to the **VAPID key it enrolled with**, and the browser never learns that key has changed: `getSubscription()` goes on returning a valid object every push service will refuse for the rest of its life, and `subscribe()` with a different `applicationServerKey` throws `InvalidStateError` — so switching push off and on again failed at the one call anybody would try. Changing the key (setting `VAPID_PRIVATE_KEY` after first boot, or losing the `server_settings` row that holds the minted one) therefore broke every enrolled device at once, permanently and silently. `syncPushSubscription` now fetches the public key on **every** load, not only when no subscription exists, and compares it against `subscription.options.applicationServerKey`: a mismatch is retired and re-enrolled. A browser that will not say which key it used is believed rather than re-enrolled on a guess
- Delivery failures are **logged**, and were not. A push service answers every refusal with a status and a reason — 403 for a key that is not this server's, 413 for a payload over 4 KB, 429 for too many — and all of it was discarded, so an instance delivering nothing looked exactly like one with nobody to notify. `send_one` prints the status and a trimmed reason, and prunes on 403 as well as 404/410 since all three are final. Only the endpoint's **origin** is ever logged: the path is a bearer credential for that device, and anyone holding it can push to it
- Unread state has one shape: **buckets**. A channel's (`channelUnreadCounts`/`channelMentions`, with `channelRoomIds` naming its room, since a room that is not open has no other record of its channels) or a room's *loose* bucket for what has no channel — a DM, a forum post, a thread reply you are part of. `roomUnreadCounts`/`roomMentions` are **derived** from them (`lib/unreads.ts`, applied by `withRoomUnreads` in every case that touches a bucket) and never written directly. They used to be maintained side by side and drifted: opening a room wiped its ping while the channel holding the mention was still unread, so a sound came with no way to find what made it. Opening a room clears only its loose pings; a channel's stay until the channel is read. A room with anything unread wears a dot left of its row (the rail's stub pill), and a closed folder carries its rooms' dot and ping
- What counts as a mention is decided once on each side and the two must agree, or a refresh moves a ping or drops it: named directly, named through a held role (unless `suppress_role_mentions`), a **reply to you** (`content.reply_to_sender`), or **any** DM message. Client: the `m.room.message` branch of `wsHandler.ts`. Server: `mention_expr` in `read_markers.rs`. `m.reply_notification` is deliberately ignored by the client now — the reply's own message carries the ping, on its channel. `GET /api/unreads` skips redacted messages, and gives a room with text channels no channel-less bucket, since nothing there could ever be read. A refetch never marks the channel on screen unread (`bucketsFromServer`): the stored marker trails the screen by a debounce
- A thread's unread mentions are its **own**: `read_markers` holds a marker per thread as well as per channel (`MarkReadRequest.thread_id`, and the stored doc names whichever it covers — the unread scan reads every marker a user owns in one pass and cannot tell a thread id from a channel id by looking at it), and `GET /api/unreads` answers a `thread_mentions` array beside `unreads`, grouped by the marker a thread shares so the scan is one aggregation per distinct marker rather than one per thread. Moving the *channel's* marker must not dismiss a thread mention: a reply is not in the channel's timeline, so scrolling the channel never showed one. `openThread` is what moves the thread's marker, and `OPEN_THREAD` zeroes the client's `threadMentions` (keyed by thread_id, global across rooms) for the same reason — the marker is what keeps the badge gone after a reload. The channel list draws it as the same `bg-destructive` pill a channel wears, on the thread's preview row; `m.thread.message` raises it live unless the reader is already in that thread, and the raise sits outside the current-room guard because the map is keyed by thread
- Reading syncs across a user's devices. When `mark_read` moves a marker it sends `read_marker` to **every** connection the user has (`broadcast_read_marker`), carrying what is *still* unread in that one bucket after the new position — counted by the same `channel_tally` / `thread_mention_tally` that `GET /api/unreads` uses — never a bare "clear", so a message that arrived after the point read stays unread elsewhere. `APPLY_READ_MARKER` replaces only that bucket and, like `bucketsFromServer`, leaves the bucket on screen alone. The same broadcast closes that channel's or thread's notifications (`closeReadNotifications`) only where the message they announce is at or before `last_read_ts` — in-page ones by the message's `origin_server_ts`, service-worker ones by the `ts` the push payload now carries (server time, so device clocks never enter into it). A device whose socket was down when the read happened (a backgrounded phone) catches up in `loadUnreads`, which closes channel notifications whose bucket came back empty (`closeNotificationsReadElsewhere`); threads are skipped there because their unread state is counted in mentions only. A phone that is never opened keeps its tray: dismissing it would take a silent push, which iOS punishes by revoking the subscription
